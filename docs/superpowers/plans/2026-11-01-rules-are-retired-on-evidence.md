# A rule clause that no longer changes behaviour is tried and removed at each release — Implementation Plan

> **For agentic workers:** execute task by task, in order. Read the whole plan first,
> including *Decisions* and *Traps*. Nothing in it stops for the developer.

**Goal:** before each of this repository's releases, the maintainer is shown how much
each rule file in `rules/` grew since the last release, picks one clause from the file
that grew most, and has a fresh agent do a real task in that clause's area with the
clause removed. The outcome goes in a committed record, `docs/rule-trials.md`, one entry
per release; a clause the agent did not need is removed from `rules/` through an ordinary
branch and pull request whose commit body carries the trial as its fresh-agent check.
`/release` in this repository runs the trial before its Stage 1.

**Spec:** the entry `rules-are-retired-on-evidence` in `feature-catalog.yaml` (band B in
`docs/backlog-board/bands.yaml`). There is no design document; the entry's five
acceptance criteria and the decisions below are the design. The comment above the entry
records the developer's decision of 2026-10-16: the trial happens at **the framework's own
release**, not in projects, and a clause removed there goes out in that release's notes.

## Decisions

### 1. Where the trial lives, and what it is

The trial is this repository's own step, like `/absorb-flush`: a new command
`.claude/commands/rule-trial.md`, a script `.github/scripts/rule-trial.mjs`, a record
`docs/rule-trials.md`, and a unit guard `guards/rule-trial.test.js`. Nothing ships to
projects: the shipped `commands/release.md` and `rules/` are untouched. `/release` here
reaches it through one new line in its project-owned block (Decision 5).

A trial is **one** fresh agent run with the clause removed. The spike
`rule-is-measured-with-and-without` may later make it a repeatable with-and-without
comparison; the command's *Run* section is the one place that would change, so write it as
its own section.

### 2. The script, `.github/scripts/rule-trial.mjs`

First comment: what it is, that it is this repository's own and is not shipped, and its
two commands. Exports these pure functions, and runs a CLI only when executed directly:

- `wordCount(text)` — number of whitespace-separated tokens (`text.split(/\s+/).filter(Boolean).length`).
- `rankGrowth(rows)` — takes `[{ file, before, after }]` (`before` is 0 for a file absent
  at the tag), returns new objects with `delta = after - before`, sorted by `delta`
  descending, then `file` ascending.
- `parseRecord(text)` — reads the record format below and returns
  `[{ heading, fields: { <name>: <value> }, clauses: <number of Clause lines>, line }]`
  in file order. A field is a line `- <Name>: <value>` directly under a `## ` heading;
  following lines indented by at least two spaces continue its value (joined with one
  space, trimmed). Text before the first `## ` heading is ignored.
- `recordProblems(entries)` — returns an array of messages, empty when the record is
  sound. Each message names the heading. Problems:
  - a heading that is not `Since v<X>.<Y>.<Z>` → `"<heading>": a heading names the release the trial ran after, as "Since vX.Y.Z"`;
  - a heading that appears twice → `"<heading>" appears twice: one trial per release`;
  - more than one `Clause` field under one heading → `"<heading>" tries more than one clause: one per release`;
  - `Outcome` missing or not one of `kept`, `removed`, `inconclusive`, `skipped` → `"<heading>": Outcome must be kept, removed, inconclusive or skipped`;
  - for `skipped`: `Why` missing or empty;
  - otherwise: any of `Rule file`, `Clause`, `Task`, `What the agent did`, `Ran on`
    missing or empty → `"<heading>": missing <field>`;
  - two entries, not skipped, with the same `Rule file` and `Clause`, where the earlier
    one in file order is `kept` → `"<later heading>" tries again a clause kept at "<earlier heading>"`.
- `triedFrom(entries, file)` — the non-skipped entries whose `Rule file` is `file`
  (compare after stripping backticks), as `{ heading, outcome, clause }`.

CLI, run from the repository root:

- `node .github/scripts/rule-trial.mjs check [record]` — reads `record` (default
  `docs/rule-trials.md`), prints each problem on its own line and exits 1, or prints
  `rule-trials: <n> trials, no problems` and exits 0.
- `node .github/scripts/rule-trial.mjs growth <tag>` — refuses with exit 1 and
  `<tag> is not a commit here` when `git rev-parse --verify --quiet <tag>^{commit}` fails.
  Otherwise takes the `.md` files under `rules/` at `HEAD` and at `<tag>`
  (`git ls-tree --name-only <rev> rules/`), measures each with `git show <rev>:<path>`
  (0 for a file absent at that revision), and prints:

  ```
  Rule files since v0.7.3, by growth in words:
    rules/planning.md        4917 → 5102   +185
    rules/tests.md            696 →  696     +0
  ```

  then, for the first row: `Tried before from rules/planning.md:` followed by one line
  per `triedFrom` entry (`  <heading>  <outcome>  <clause>`), or
  `Nothing tried before from rules/planning.md.` When the first row's delta is 0 or less,
  print instead as the last line `No rule file grew since <tag>: record a skipped trial.`
  It reads the record from `docs/rule-trials.md` and, when the record has problems,
  prints them and exits 1 before the table. Column alignment is yours.

### 3. The record, `docs/rule-trials.md`

Create it with a heading `# Rule trials`, two or three sentences saying what it is (one
entry per release of this repository: the clause tried, the task, what the agent did and
the outcome; written by `/rule-trial`, checked by `node .github/scripts/rule-trial.mjs check`),
then this format as a fenced example, and no entries:

```
## Since v0.7.3

- Rule file: `rules/planning.md`
- Clause: "A plan names the checkouts it may touch" — the bold lead or first sentence, quoted
- Task: what the agent was asked, in one or two sentences
- What the agent did: the tool calls that bear on the clause, and their answers
- Outcome: kept | removed | inconclusive | skipped
- Ran on: tool and version, operating system and architecture
- Why: only for skipped
```

The parser must not read the fenced example as an entry: skip lines inside a ``` fence.

### 4. The command, `.claude/commands/rule-trial.md`

Frontmatter `description: "Before a release of this repository, try one rule clause with a fresh agent that does not receive it, record the outcome, and remove the clause if the agent did not need it."`
Opening paragraph: this command lives in this repository only and never ships; it runs
from `/release` before Stage 1 (this repository's project-owned block), takes the last
release tag, tries **one** clause, and starts nothing without the developer's yes. Then
these sections, in your words, covering every point:

1. **Measure.** `node .github/scripts/rule-trial.mjs growth <tag>`; on exit 1, show the
   output and stop. Show the table. When it says no rule file grew, propose a skipped
   entry with that reason and go to *Record*.
2. **Choose the clause.** From the top file only. Read `git diff <tag> HEAD -- <file>`:
   prefer a clause added or changed since the tag. A clause is one whole instruction — a
   bullet or a paragraph under a heading — never a heading's whole section. Not a clause
   the *Tried before* list shows as `kept`. Propose it to the developer, quoted, with the
   task (next point) and what tripping would look like; wait. The developer may choose
   another clause from the same file, or skip (record `skipped` with their reason).
3. **Design the task.** A real task that makes the agent touch files in the rule's area
   (`.claude/rule-areas.json` names the patterns), so the rule is delivered; an agent that
   only discusses a clause never receives it. The situation the clause governs must arise
   in the task. The subject is invented, never a backlog entry, and the prompt says the
   output is a probe and will be discarded. Before running, write down what an agent that
   had the clause would do, and what tripping over its absence looks like.
4. **Set up the scratch copy.** A clone, never a worktree of this checkout and never the
   branch you are on: `T="$(mktemp -d)"; git clone -q "$PWD" "$T/tropis"; git -C "$T/tropis" remote remove origin`.
   Copy every `rules/*.md` into `$T/tropis/.tropis/rules/`, delete the clause from the
   chosen one there, run `node .tropis/scripts/generate-rules.mjs` inside `$T/tropis`, and
   confirm with `grep` that `$T/tropis/.claude/rules/<name>.md` lacks the clause and the
   other rule files carry the next release's text. Say why: the installed rules are the
   last release's, so without the copy the agent would receive neither the clause nor
   what grew around it.
5. **Run.** Before running, check that the developer's own user-level instructions do not
   say what the clause says; if they do, run where they do not load, such as a cloud
   session, and say so. From `$T/tropis`, pipe the prompt to a fresh agent with its tool
   calls visible — in Claude Code, `claude -p --output-format stream-json --verbose`,
   saving the output to a file. One run.
6. **Judge by what it did, not what it says.** Read its tool calls. It did what the
   clause asks without having it → `removed`. It did what the clause exists to prevent →
   `kept`. The situation never arose → `inconclusive`; nothing is removed. Quote the calls
   that decided it. Put the verdict to the developer as a recommendation and wait.
7. **Record, and remove.** On a branch in a worktree of its own (workflow.md,
   *Branching*), add the entry to `docs/rule-trials.md` under `## Since <tag>`, run
   `node .github/scripts/rule-trial.mjs check`. On `removed`, the same branch deletes the
   clause from `rules/<file>.md`, runs `bash scripts/check-blueprint.sh` after committing
   (a guard may cite the clause), and the commit body states what the trial agent was
   asked, what it did, and the tool, version, operating system and architecture — the
   trial is that change's fresh-agent check, so a removal goes the way any rule change
   goes. Then push, open the pull request, `gh pr merge <N> --auto --squash` with
   `--subject` and `--body`, and `node .tropis/scripts/main-status.mjs --pull-request <N>`;
   go back to `/release` only once it reports the main branch green. Remove the worktree
   and `$T`.
8. **For the notes.** Where a clause was removed, tell `/release` so Stage 3 says which
   rule no longer says what, under the closing small-corrections heading.

Do not write the literal command that creates a worktree in this file's text beyond the
reference to workflow.md: name the rule, as above.
